# Angular / TypeScript standards
- Standalone components, lazy feature routes, strict TypeScript, typed Reactive Forms, typed API interfaces, no `any` without justification.
- Prefer signals for local synchronous state and RxJS/HttpClient for HTTP. Avoid adding a global state library for this assessment.
- Use `inject()`, OnPush where suitable, modern Angular control flow, `track` in repeated templates; follow installed Angular version's official style guide.
- Organize feature pages, reusable presentational components and data-access services by feature. Keep templates readable and avoid business rules duplicated from backend.
- Build customer flow: account dashboard → transactions list (with account selector) → transaction detail → dispute form → history → dispute detail and customer-safe decision.
- Build agent flow: unassigned queue, mine, all, case detail, claim, release, resolve with internal notes and customer message.
- **Design reference:** https://www.capitecbank.co.za/personal/insure/life-cover/ . Match its public web design language for a desktop-first responsive portal, not its mobile app and not a generic admin template. Use `docs/design/ui-flows.md` for screen-specific requirements. An AI-generated mobile mockup is not a source of truth: do not copy its labels, field names, merchant categories, card details, account names or number formats. Account labels are "Main Account" and "Savings Account" only.
- Reference structure confirmed from the public page: utility navigation (Personal/Business, search, sign-in, app/account CTAs); product-category navigation (Transact/Save/Insure/Credit/Connect/Rewards); a concise page hero with a clear heading, supporting copy and CTA; distinct content sections; accordions for expandable information; and a multi-column footer that becomes collapsible groups on narrow layouts.
- Apply those patterns selectively: use a **simplified authenticated application header** with role-aware links and sign-out, not the entire public marketing mega-menu. Use a restrained app footer rather than copying all public marketing/legal links. Agent screens may use a sidebar and data table for productivity.
- Build **desktop-first** layouts, then adapt at tablet and mobile widths. Customer lists may become stacked rows/cards; agent tables must retain usable filtering and actions without horizontal overflow or hover-only controls.
- Centralize SCSS design tokens for typography, spacing, colours, radii, elevation, button variants and breakpoints. **Measured from user-supplied Capitec website CSS:** NunitoSans/Arial/Helvetica; body text #3A3A3A; primary/link blue #2F70EF; link hover #2259D0; background #F7F7F7; white #FFFFFF; secondary button white with blue text and border. Do not use the earlier provisional #00486D/#F4F6F8 palette as if it matched this reference. Some tokens are CSS custom properties, not proof of every element’s computed style.
- **Font:** use Nunito Sans (weights verified only as light 300 in supplied @font-face snippet; verify additional weights before specifying them) with Arial/Helvetica fallback. Obtain font from a properly licensed distribution; do not copy Capitec-hosted font assets. **Responsive evidence:** hero top padding 70px above 991px, 30px at <=991px; framework breakpoints 576/768/992/1200px are available but not proof of each component breakpoint. Exact icon library, icon sizes, header/footer heights, heading typography and general section spacing scale remain unverified. Button geometry and desktop navigation spacing have now been evidenced separately. Use a consistent accessible icon set (e.g. Lucide) as our own choice, not a claimed match.
- **Measured button CSS:** standard `.button--v2` height 48px, min-width 144px, border-radius 24px, padding 14.5px 24px, 1.5px solid #2F70EF, NunitoSans 16px weight 600, inline-flex centered. Secondary is white with blue text/border. `.button--v2--small`: 30px height, 15px radius, 6.5px 15px padding, 14px font; desktop nav CTA at >=992px overrides to height 36px, min-width 116px, radius 30px, font-size 16px and auto width. These are reference measurements; use accessible touch targets for our app rather than forcing small controls on mobile.
- **Measured desktop nav CSS:** `.primary-nav` flex, nowrap, center-aligned, gap 20px, justify-content space-between; margins 15px each side, becoming 40px at >=992px. Screenshot shows white utility bar, pill CTAs, Personal/Business segmented switch, search and sign-in, and a large multi-column mega-menu overlay. Our app adopts the styling, not the entire marketing navigation.
- **Icons:** use our own consistent icon set (Lucide recommended), not Capitec-owned icon assets.
- Buttons: distinguish primary, secondary, text and destructive actions; consistent padding and focus states. Navigation, CTA prominence, simple section rhythm and responsive footer behaviour should feel like the reference, without copying proprietary assets or implying official affiliation.
- Avoid unrequested marketing hero imagery inside authenticated transaction and case-management screens. Preserve content density appropriate to banking workflows.
- Use semantic HTML, labels, keyboard focus, accessible contrast, responsive layouts, error and loading states.
- Never bypass sanitization or render arbitrary HTML. Authentication uses an opaque HttpOnly session cookie; no JWTs, localStorage authentication tokens or bearer-token interceptors. Keep only non-secret current-user/UI state in Angular; backend authorization is authoritative.
- Distinguish eligible, already-disputed, pending and failed transactions in UI; display useful 409/412 recovery paths.
- Agent detail ETag/If-Match is approved: retain opaque tag, send on all agent mutations, replace after success; refresh on 412/409 and never blind retry with a new tag. Terminal cases are read-only; customer DTOs never contain assignment.
- Consume custom `{status,data,error_code}` envelopes and 1-based `{total,page,size,items}` collections; domain status lives inside data. Implement the API collection search/filter/sort controls with debounce, combined queries and pagination reset. The account selector is a shared presentational component in `shared/components` whose inputs are the accounts list and the current selectedAccountId; it emits a selection-change event. Account data fetching stays in the feature, not the shared component. The URL is the only account selection state (no localStorage/sessionStorage); /customer/transactions without accountId resolves the primary account and rewrites the URL with `history.replace`; changing the selector updates accountId and resets to page 1. Do not poll, prefetch, auto-refresh or auto-retry requests triggered by the selector or any other navigation.
- Keep creation key on unchanged network retry; generate a new key only for changed submissions. Reload may resume a still-valid server-side session; do not force login solely on reload. Server-enforced 30-minute idle expiry or sign-out clears sensitive cached state and leads to login; allow only validated role-appropriate return routes. AuthService bootstraps CSRF then resolves identity at startup; generation checks discard stale responses. Confirmed logout clears identity; transport/store ambiguity hides private views and requires explicit retry. Handle non-JSON proxy/network errors safely.

- Same-origin /api/v1 requests use the browser session cookie. Unsafe requests, including login/logout, require CSRF; masked CSRF material is held only in memory and sent as X-CSRF-TOKEN on same-origin unsafe API requests. Never automatically replay unsafe requests. A CSRF token is not an authentication token and must not expose the HttpOnly session identifier.
