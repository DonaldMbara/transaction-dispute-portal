# Authentication operations and local verification

Follow the root [README](../../README.md) for Java 21, Maven 3.9+, Node from frontend/.nvmrc, PostgreSQL Compose and same-origin Angular proxy startup. Compose interpolation does not export native backend variables: load only a trusted ignored root `.env` with `set -a`, `source .env`, `set +a`. It supplies DB_URL/DB_USERNAME/DB_PASSWORD and explicit SPRING_PROFILES_ACTIVE=local; never account passwords. Start only PostgreSQL with `docker compose up -d postgres`, run the backend on localhost:8080, and `npm start` from frontend on localhost:4200. Use the browser at port 4200. No separate cross-origin backend URL, CORS or bearer header is needed.

Provision a synthetic account only through the [non-web masked-console procedure](account-provisioning.md), invoked explicitly after building the backend JAR. Obtain trusted host/database privileges and a secure one-to-one credential-delivery channel. There are no default accounts. Sign in with that account through the Angular form. CUSTOMER opens /customer and AGENT /agent; these are foundation landing areas, with business workflows still deferred.

Session cookie configuration is SESSION, host-only, HttpOnly, SameSite=Lax, /api/v1, browser lifetime. Production/default Secure=true remains independent of forwarded headers; use the explicit production profile with an HTTPS boundary. Only local permits Secure=false; production+local or insecure non-local overrides fail startup. Do not put session cookies, CSRF material or request bodies in troubleshooting logs. An HTTPS test fixture is verification tooling, not an application deployment topology.

GET /api/v1/auth/csrf returns masked material and X-CSRF-TOKEN inside the envelope; Angular holds it in memory and attaches it only to same-origin unsafe API requests. Login/logout require it and clear prior material. Bootstrap after each confirmed transition before further unsafe actions. A confirmed login/logout with failed bootstrap retains the outcome and blocks unsafe operations until explicit token retry. A 403/1010 means verification failed; never automatically replay credential submissions or future business writes. A 401 clears private state; a permission 403 or store 503 does not prove logout.

If sign-out is transport/store ambiguous, protected views are hidden and the UI states it was not confirmed. Retry deliberately: bootstrap fresh anonymous/current-session CSRF, then submit logout once. The server's repeated fresh-token logout is idempotent, but a network failure is never confirmation. GET logout has no effect. Independent browser sessions remain valid unless operational account changes revoke them.

The authoritative idle deadline is 1,800 seconds after eligible handler admission. Only identity currently qualifies; no automatic identity polling is used. Later validation/handler errors still count once the authorized interaction is admitted. Bootstrap, logout, health, denied/unmatched/background requests never keep authentication alive. Deadline equality expires even if a row remains physically stored. SQL guards use PostgreSQL time; captured framework timestamps originate on backend hosts, so synchronize all hosts/database clocks with operational time synchronization. No additional skew allowance is configured.

SESSION_CLEANUP_CRON controls framework expiry cleanup and AUTH_ACTIVITY_CLEANUP_CRON controls strict activity cleanup; both default to `0 * * * * *`. Set `-` only when deliberately disabling scheduled cleanup (deterministic tests do this). Activity cleanup deletes expired parent sessions with cascading attributes/activity; unexpired anonymous CSRF sessions survive. Request-time validation remains authoritative regardless of cleanup timing. Database timeouts are bounded: pool connection 5 s, validation 2 s, JDBC socket/statement/query 5 s; tests may shorten them independently. These are assessment bounds, not production latency guarantees.

Compatible backend instances use the same database/schema, principal serial form, cookie settings and encoder mapping. No sticky routing or in-memory fallback is required. Unexpired sessions restore after restart. Incompatible serialized-principal releases require a reviewed invalidation rollout. Restrict access to serialized session data; never deserialize attacker-controlled database content by assuming it is trusted.

Operational disable/enable/role/password replacements atomically increment auth_version; every older session fails on its next protected request after commit. Re-enable does not resurrect it. Hashing happens outside account-row locks where feasible; optimistic version preconditions reject lost updates without increments. Requests already authorized before the administrative commit may finish as specified. Trusted account deletion also revokes, but future banking-history constraints may require disable instead of deletion.

Store failures before response commitment return generic 503/3002. Framework pre-commit saves are tested through the ordinary wrapper/filter boundary. Once headers/body physically commit, the server cannot replace status/cookies: a subsequent persistence fault is logged with a safe correlation and may terminate the body. Treat incomplete transport as unconfirmed; recheck actual persisted state after storage recovery rather than blindly repeating a mutation. Readiness becomes 503/DOWN while liveness remains UP. Recovery tests preserve storage and revalidate the session; session survival after database data loss is not promised.

PBKDF2 benchmark: Java 21.0.12.1, Intel i7-8750H, 6 cores/12 logical processors, Linux amd64, two warm-up pairs/five samples, 600,000 iterations. Encode min/median/max 557.778/573.409/612.123 ms; verify 551.993/571.946/610.010 ms. No password/hash output is included. Rerun on deployment hardware and assess capacity/abuse controls in hardening; do not silently lower parameters. Parameter changes require a new encoder identifier.

Authentication and provisioning outcome logs contain timestamps, operation/outcome and non-sensitive account/correlation/operator references where known. Restrict retention/access. Ordinary logs and database commits are not crash-atomic; an interrupted operational command requires trusted inspection before retry, as the provisioning runbook explains. Never enable credential body, JDBC bind or session/cookie/token logging. MFA, recovery, rate-limit infrastructure, stronger durable audit and production proxy deployment remain separate approved work.
